# Наблюдаемость

Сервер пишет структурированные JSON-логи через pino в stdout. В записи есть
`requestId`, метод, путь без query-строки, статус, длительность и `userId` для
аутентифицированных запросов. Заголовки `Authorization`/`Cookie`, пароли и
токены вырезаются на уровне логгера.

Каждый ответ API получает `X-Request-Id`. Входящий `X-Request-Id` принимается
только в безопасном формате. Необработанные ошибки логируются со stack trace и
тем же `requestId`, а наружу отдаётся безопасное сообщение.

`WAKANDA_LOG_LEVEL` задаёт уровень: `fatal`, `error`, `warn`, `info`, `debug`,
`trace` или `silent`. `WAKANDA_RELEASE` добавляет метку релиза серверных логов,
`VITE_RELEASE` — клиентских сообщений (передаётся на сборке образа).

Ошибки React, глобальные `error`/`unhandledrejection` и сбои lazy-чанков в
production отправляются на `POST /api/client-errors` (лимитировано; query-строка
и пользовательские данные не передаются) и попадают в общий лог.

Логи можно читать глазами или отправлять в journald/Loki/CloudWatch без
дополнительного парсера. Состояние пользователя и секреты в логи не попадают.
Статус планировщика виден в `GET /api/health` (`scheduler`): готовность Web Push
и Telegram, время последнего запуска/успеха и флаг ошибки; текст ошибки остаётся
в логах.
